## Scenario-Based Questions

### Question 1
You run the command `sudo du -sh /` on a server to get a total capacity reading. The process hangs for several minutes, outputs dozens of permission warnings, and finally displays a size of 150GB. However, `df -h` shows that your local physical SSD `/dev/vda1` is only 15GB in size. What caused `du` to report an incorrect, inflated size?
*   **A)** The local root drive has bad sectors.
*   **B)** You did not run `fsck` first to clean the indexing caches.
*   **C)** Naive `du` walked across your mount points, traversing into large mounted external drives and remote network shares, adding their contents to your root total.
*   **D)** The `du` command is only capable of reading block sizes, not file sizes.

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: C**

*   **Why C is correct:** By default, `du` recursively traverses every single directory branch starting from your target path. If you target the root `/` directory, `du` will cross over your mount boundaries, walking into separate drives, backup disks, or massive network mounts (like NFS or SSHFS), summing all their sizes into your local root calculation. To restrict `du`'s measurement scales to your single, local root disk, you **must** use the `-x` (or `--one-file-system`) flag.
*   **Why others are incorrect:**
    *   *Option A* is incorrect because bad sectors cause I/O read timeouts, not silent size inflation.
    *   *Option B* is incorrect because filesystem integrity checks do not alter capacity reporting.
    *   *Option D* is incorrect because `du` is specifically designed to calculate exact file and directory storage allocations.
</details>

### Question 2
You are preparing a sorted capacity report of top-level directories under `/`. You want to limit the output display to only the direct subdirectories of `/` (e.g., `/home`, `/var`), with sizes formatted in human-readable units. Which command is correctly formulated?
*   **A)** `sudo du -sh /`
*   **B)** `sudo du -xh --max-depth=1 /`
*   **C)** `sudo du -h -d 2 /`
*   **D)** `sudo du --max-depth=1 /etc`

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: B**

*   **Why B is correct:** To limit the displayed directory depth in `du`, you use the `--max-depth=` (or `-d`) parameter. Setting depth to `1` restricts output to only the top-level directories directly under `/`. The `-h` flag formats sizes cleanly into K, M, and G units, and `-x` ensures separate drives are ignored.
*   **Why others are incorrect:**
    *   *Option A* is incorrect because `-s` (summarize) outputs only a single line for `/` itself, hiding all subfolders.
    *   *Option C* is incorrect because a depth of `2` will output the nested subdirectories of subdirectories (e.g., `/var/log`, `/var/lib`), cluttering the report.
    *   *Option D* is incorrect because it targets `/etc`, not the root directory `/`.
</details>

### Question 3
You want to sort a list of directory sizes generated by `du -h`. If you use the standard numerical sort (`sort -n`), a folder showing a size of `15M` gets sorted *above* a folder showing a size of `2G`. How do you resolve this sorting error?
*   **A)** Use `sort -h` to make the sorting utility aware of human-readable suffixes.
*   **B)** Format the files to XFS to standardize the indexing blocks.
*   **C)** Run `sort -r` to force alphabetical matching.
*   **D)** Convert all sizes to kilobytes manually before running the sort.

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: A**

*   **Why A is correct:** Standard numerical sorting (`sort -n`) only compares digits; it is unaware of unit suffixes like `M` (Megabytes) or `G` (Gigabytes). Since `15` is larger than `2`, it places `15M` above `2G`. Using `sort -h` tells the sorting utility to parse human-readable suffix multiplier values, ensuring `2G` is correctly sorted as larger than `15M`.
*   **Why others are incorrect:**
    *   *Option B* is incorrect because filesystem formats have no influence over shell string sorting tools.
    *   *Option C* is incorrect because alphabetical reverse sorting does not resolve numeric multiplier calculations.
    *   *Option D* is incorrect because manually converting blocks is extremely tedious, labor-intensive, and prone to administrative error.
</details>

### Question 4
You have a symbolic link located at `/opt/active` that points to a physical database folder located at `/var/lib/database/prod`. You want to delete the symbolic link pointer, but you must ensure the physical database folder and its files are left completely untouched. Which command is safe to execute?
*   **A)** `rm -rf /opt/active/`
*   **B)** `rm /opt/active`
*   **C)** `rmdir /opt/active`
*   **D)** `unlink /var/lib/database/prod`

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: B**

*   **Why B is correct:** This is a high-stakes administrator trap. A symbolic link is a special pointer file. Running a basic delete command `rm /opt/active` (with **no trailing slash**) safely removes the pointer file itself, leaving the target directory `/var/lib/database/prod` untouched. 
*   **Why others are incorrect:**
    *   *Option A* is highly destructive. Because you added a trailing slash (`/opt/active/`), the shell dereferences the symlink and enters the target folder, recursively deleting all files inside `/var/lib/database/prod` before you can stop it.
    *   *Option C* is incorrect because `rmdir` is designed to delete empty directories, not file pointers, and will fail.
    *   *Option D* is incorrect because it runs the unlink command on the physical target, not the link pointer.
</details>

### Question 5
You need to identify all symbolic links located directly under the `/` directory, ignoring any links nested deeper in subdirectories. Which command should you run?
*   **A)** `find / -type l`
*   **B)** `find / -maxdepth 1 -type l`
*   **C)** `ls -la / | grep symlink`
*   **D)** `file /`

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: B**

*   **Why B is correct:** The `find` utility search can be restricted using depth parameters. Setting `-maxdepth 1` tells the tool to search strictly within the root `/` folder itself, immediately stopping and ignoring subdirectories. The `-type l` flag limits results to symbolic links.
*   **Why others are incorrect:**
    *   *Option A* is incorrect because omitting the depth limit will cause `find` to recursively scan every folder in your entire hard drive, taking a long time and outputting millions of nested links.
    *   *Option C* is incorrect because standard `grep` for the word "symlink" fails as `ls -la` outputs links formatted with arrows (`->`), not the word "symlink".
    *   *Option D* is incorrect because `file /` simply reports that `/` is a directory.
</details>

## Disk Quotas (Modules 2–3)

### Question 6
You added `usrquota,grpquota` to the `/home` line in `/etc/fstab` and remounted, but `quotaon /home` reports that quotas are not initialised. What step is missing?
*   **A)** Reboot — quota options only apply at boot.
*   **B)** Run `quotacheck -cug /home` to create the accounting files before enabling enforcement.
*   **C)** Run `mkfs.ext4` again with a quota feature flag.
*   **D)** Add the users to `/etc/quotatab`.

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: B**

*   **Why B is correct:** On ext4, enforcement (`quotaon`) needs the accounting files (`aquota.user` / `aquota.group`) at the filesystem root. `quotacheck -cug <fs>`, run once with the filesystem idle, scans current usage and creates them. After that, `quotaon` works.
*   **Why others are incorrect:**
    *   *Option A* — a remount applies the options fine; the missing piece is the accounting files.
    *   *Option C* — reformatting would destroy the data and is not required.
    *   *Option D* — there is no `/etc/quotatab`; quota records live in the accounting files.
</details>

### Question 7
A user's quota is `soft=2G`, `hard=3G`. They are currently using 2.4G. What is happening?
*   **A)** Writes are already blocked; they must delete files to write again.
*   **B)** Writes still succeed, but a grace-period countdown has started; if they are still over 2G when it expires, the soft limit starts acting like a hard one.
*   **C)** Nothing — soft limits are advisory and never enforced.
*   **D)** The hard limit has been automatically raised to 4G.

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: B**

*   **Why B is correct:** Between the soft and hard limits, writes continue but the filesystem starts a grace timer. If the user drops back under the soft limit before it expires, nothing happens. If the timer reaches zero while they are still over soft, further allocation is refused until they get back under soft — the soft limit effectively becomes a hard limit.
*   **Why others are incorrect:**
    *   *Option A* — the hard limit (3G) has not been reached, so writes are not yet blocked.
    *   *Option C* — soft limits are enforced, via the grace mechanism.
    *   *Option D* — limits are not adjusted automatically.
</details>

### Question 8
Which statement about enabling quotas on an **XFS** filesystem is correct?
*   **A)** Run `quotacheck` then `quotaon`, the same as ext4.
*   **B)** Quotas are enabled by mounting with an option such as `uquota` or `pquota`; there is no `quotacheck`.
*   **C)** XFS does not support quotas.
*   **D)** You must convert the filesystem to ext4 first.

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: B**

*   **Why B is correct:** XFS keeps quota usage in internal metadata and turns quotas on at mount time based on options like `uquota` (user), `gquota` (group), `pquota` (project). There are no `aquota.*` files and no `quotacheck` step; `xfs_quota` is used to set and report limits.
*   **Why others are incorrect:**
    *   *Option A* — `quotacheck`/`quotaon` and `aquota.*` files are the ext2/3/4 model, not XFS.
    *   *Option C* — XFS has full quota support, including project quotas.
    *   *Option D* — no conversion is needed.
</details>

### Question 9
You want the directory `/srv/www/site` to use no more than 10 GB total, no matter which users create files in it. Which quota type does this, and where is the directory-to-ID mapping defined?
*   **A)** A group quota; defined in `/etc/group`.
*   **B)** A user quota on each user; defined in `/etc/passwd`.
*   **C)** A project quota; the ID-to-path mapping goes in `/etc/projects` (with a name in `/etc/projid`).
*   **D)** An inode quota; defined in the superblock.

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: C**

*   **Why C is correct:** A project quota attaches a numeric ID to a directory tree; every file under it inherits the ID, and the project's limit caps the whole tree regardless of file ownership. `/etc/projects` holds `<id>:<path>`; `/etc/projid` gives the ID a name. `xfs_quota -x -c 'project -s <name>'` initialises it, then `limit -p bhard=10g <name>` sets the cap.
*   **Why others are incorrect:**
    *   *Option A* — a group quota limits files owned by a group, not a directory, and users could create files under other groups.
    *   *Option B* — per-user quotas do not bound a shared directory's total.
    *   *Option D* — an inode quota limits file *count*, not space, and is not directory-scoped.
</details>

### Question 10
On a filesystem with enforced quotas, a process running as **root** writes a 5 GB file into a user's directory whose quota is 1 GB. What happens?
*   **A)** The write fails at 1 GB — quotas apply to everyone.
*   **B)** The write succeeds — quota enforcement does not apply to root.
*   **C)** The file is created but immediately deleted by the quota daemon.
*   **D)** The user's quota is automatically raised to 5 GB.

<details>
<summary><b>Reveal Correct Answer & Teacher's Explanation</b></summary>

**Correct Answer: B**

*   **Why B is correct:** Quota enforcement is bypassed for UID 0. Root can write past any user's or project's limit. This is why you always test quota enforcement as an unprivileged user (`sudo -u alice ...`), and why a runaway root process can still fill a quota-managed filesystem.
*   **Why others are incorrect:**
    *   *Option A* — root is exempt from enforcement.
    *   *Option C* — there is no daemon that deletes over-quota files.
    *   *Option D* — quotas are never raised automatically.
</details>
